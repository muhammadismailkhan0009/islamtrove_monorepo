# Published Quran passage groupings

## Purpose

A visitor may use either personal (browser-local) Surah passage groupings or
administrator-published groupings. The selector is in **Listening Settings →
Grouping library** (and the **Groupings** button in the listening summary).

Published groupings are used by default whenever a Surah is opened, including
when switching from another Surah. Local selection is temporary for the
currently open Surah; switching Surahs or reloading returns to published
defaults. If a Surah has no published grouping, play the locally bundled
**QPC thematic passages** (1266 Quranic Passage Collection groups, normalized
to cover all Ayahs exactly once). If that Surah's QPC metadata is missing or
invalid, use its traditional **Rukūʿ boundaries**; as a last resort, play the
whole Surah. Saved local edits remain available on the device and are never
overwritten by the published selection.

The two collections are independent:

- **My local groupings** are the user's saved per-Surah breakpoint arrays in
  `localStorage`. Selecting Local for the current Surah creates its starter
  grouping if absent; editing the breakpoint grid changes only that local version.
- **Published groupings** are read-only, publicly available server data. Selecting
  the published source changes the listening queue but never overwrites local
  boundaries. A Surah without a published grouping uses QPC thematic passage
  endings; if those are invalid or missing it uses Rukūʿ boundaries.
  Click **Use this as my local grouping** to create an editable copy.
- A shared link (`?surah=18&translation_lang=ur&autoplay=true`) prefers the
  published grouping for its Surah if available. The source and audio parameters
  of a shared link do not overwrite the receiver's stored preferences.

## QPC thematic fallback (default when no published grouping exists)

- Source: Qur'an QA 2023 **Thematic Quranic Passage Collection v1.1**,
  [QPC source TSV](https://gitlab.com/bigirqu/quran-qa-2023/-/blob/main/Task-A/data/Thematic_QPC/QQA23_TaskA_QPC_v1.1.tsv).
  Vendored, unmodified source: `frontend/data/qpc/QQA23_TaskA_QPC_v1.1.tsv`.
- Offline generator: `python3 frontend/tools/generate_qpc_boundaries.py`
  (no network request required). Generated runtime module:
  `frontend/src/features/listening-studio/qpc-boundaries.ts`.
  Use `python3 frontend/tools/generate_qpc_boundaries.py --check` to validate
  that checked-in data still matches the source, including SHA-256.
- The generator processes ranges in **original source order**. An earlier passage
  retains ownership of its Ayahs; later overlapping passages are trimmed at
  their start, or dropped if fully covered. It never invents missing Ayahs.
  All Surahs must still cover Ayah 1 through their final Ayah, without gaps,
  repetition, reversed ranges, or out-of-range values.
- Verified normalized output: **114 Surahs, 1,266 passages, 6,236 Ayahs**.
  Only two source overlaps needed trimming:
  - An-Nisa (4): `11–12, 12–14` becomes `11–12, 13–14`.
  - Al-Ahzab (33): `41–44, 42–48` becomes `41–44, 45–48`.
- Listening precedence: **published boundaries (if any)** → validated QPC
  groupings → Rukūʿ → whole Surah. Local selection stays explicit and uses
  saved local edits, or starts with the same default if none exist.
- This is a **provisional listening-oriented editorial scaffold**, not
  a declaration of scholarly correctness; administrators may override each
  Surah later, without editing QPC or wiping local changes.

## Conventional Rukūʿ fallback

- Metadata: [Tanzil Project Quran Metadata v1.0](https://tanzil.net/docs/Quran_Metadata)
  ([source XML](https://tanzil.net/res/text/metadata/quran-data.xml)),
  licensed **CC BY**, attributed to the Tanzil Project.
- The source uses the **556-Rukūʿ convention**. Other metadata systems use
  558 sections; this is an editorial convention, not canonical verse division.
- `frontend/src/features/listening-studio/ruku-boundaries.ts` contains the
  114-Surah/556-boundary static dataset, generated by converting the next
  Rukūʿ's starting Ayah into the preceding Rukūʿ's ending Ayah, always ending
  at each Surah's final Ayah.
- Use these only if QPC passage data for a Surah fails validation.
  Selecting **Local** uses its saved local boundaries if available; otherwise
  it starts from the same QPC (or secondary Rukūʿ) default.
- Rukūʿs often follow a related subject but are not guaranteed to fit a desired
  listening duration. They are the starting point for future curated grouping,
  not a substitute for tafsir review.

## API contracts

`GET /api/quran/groupings`: public, non-cacheable read of:

```json
{
  "schemaVersion": 1,
  "revision": 3,
  "groupings": [
    {"surahId": 18, "boundaries": [10, 26, 44, 59, 70, 82, 98, 110]}
  ]
}
```

If nothing is published, returns revision 0 and an empty array.

`POST /api/admin/groupings/surahs/{surahId}`: upserts the **one selected
Surah's full grouping**. Other published Surahs remain unchanged, including
those with independent review/verification boundaries saved locally.

```json
{
  "expectedRevision": 3,
  "boundaries": [10, 26, 44, 59, 70, 82, 98, 110]
}
```

The Surah number comes from the URL path, and the body contains only that
Surah's complete list of passage boundaries—not the whole local collection.
The UI clearly identifies which local Surah is selected before requesting
administrator confirmation. The old whole-catalog write endpoint was removed.

Requires the existing `POST /api/admin/verify` administrator login,
HttpOnly same-site admin session cookie, `X-CSRF-Token`, and same-origin
enforcement. A stale revision or invalid grouping returns HTTP 409; invalid
input schema returns 422. On success, the endpoint returns the full updated
catalog with its revision incremented by one.

Validation checks valid Surah IDs, unique Surahs, strictly increasing integer
breakpoints within each Surah's authoritative Ayah count, and mandatory final
Ayah. No source audio, verse text, account data, or translation preferences are
included in a grouping.

## Persistence and deployment

All published groupings are stored in **`review-data/groupings.json`**, alongside
reviewed Ayah records, using an atomic file replacement under a per-process
asyncio lock. In production the existing host-mounted
`ISLAMTROVE_REVIEW_DATA_DIR` retains this file when the Docker container is
replaced. Ensure host directory permissions permit the non-root app to write.

When the file is included in versioned `backend/review-data/groupings.json`,
the Docker entrypoint seeds it on a **new host only**, without overwriting
a live published file. As with reviewed timestamps, export and manually
synchronize server data to Git after verifying it; there is no automatic
repository push.

## Development and testing

The Angular feature uses a typed `GROUPING_LIBRARY` application port.
The production adapter uses same-origin `/api`; the Design Canvas mock
adapter simulates load/login/single-Surah publication in memory, with demonstration
code `2468` that is **not valid on the real backend**.

Design Canvas preview routes remain available:
`/?groups-demo=local|server|publish|success`.

Local validation:

```bash
cd backend && uv run pytest -q && uv run ruff check . && uv run pyright
cd frontend && npm test && npm run build
```

Deployment, commits, and publishing the public host remain separate manual actions.
