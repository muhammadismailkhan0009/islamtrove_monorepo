# Project Decisions

> Durable current engineering decisions. Keep concise and current; this is not a changelog, task list, or session memory.

## Product Scope
- First release is a free, audio-first Quran listening experience: configurable Surah passages, Arabic recitation, English/Urdu/German spoken translations, reading text and per-Ayah controls.
- **Deferred enhancement (not required for initial release):** remember Surah/Ayah and playback phase across visits, with a simple one-click Continue Listening action. Implement only when prioritized after launch.
- Administrator may publish curated default passage groupings for optional use by all visitors; personal breakpoint edits remain private to each browser and must not modify published defaults. **Publish** updates only the selected Surah's complete grouping, never other local verification-only Surahs. Visitors choose local/server versions; copying a server grouping to local is explicit. Implemented with a CSRF-protected single-Surah upsert and public grouping catalog in `review-data/groupings.json`; deployment remains manual. Keep playback simple for older family members.
- Shared listening links will configure only `surah`, `translation_lang` (spoken audio, not just text), and `autoplay`; the Share button uses the active Surah and spoken languages, requesting autoplay. No Ayah or grouping URL parameter. If the browser blocks autoplay, show a single prominent, mobile-accessible Play action rather than requiring users to configure anything. Fallback serves real links; the separate `/?link-demo=blocked` Design Canvas view remains a fixed mock preview.
- Do not introduce AI, accounts, payment infrastructure, or an unrelated Islamic-content module into the listening MVP without a new decision.
- Open-source code is intended for MIT licensing; third-party Quran recordings and translated content have independent attribution/redistribution terms. Do not assume MIT applies to external media.

## Architecture
- Angular owns the listening sequence and UI; FastAPI owns trusted Quran data, validated media URLs, source-specific timelines, authenticated review writes, and proxying.
- Frontend depends on typed application ports; mock and production adapters are selected only in `frontend/src/main.ts`. Keep mock fixture data out of components and adapter implementation logic. Preserve Design Canvas managed-v2 source ownership.
- Arabic recitation uses one continuous Minshawi Mujawwad source recording per Surah, with Ayah millisecond boundaries. Do not assemble replacement audio or invent timestamp fixes. Surah 21's existing QUL-based timing was listener-confirmed.
- Fetch Arabic recording metadata and each spoken-translation language independently. Translation failures or missing Ayahs are nonfatal and must not interrupt valid Arabic listening. Never invent missing spoken clips.
- Spoken translation order and passage breakpoints are orchestrated in the browser, not through an extra backend playback-plan service.
- Arabic verse text and each written-language translation load independently; a translation provider failure must not blank Arabic text or recitation. Keep source/edition attribution accurate.

## Contracts & Data
- Canonical `backend/src/islamtrove/data/alignments/NNN.json` files are Git-versioned, immutable at runtime, and tied to the original source recording. Review/correction files in `backend/review-data/NNN.json` are **also product data** and must remain Git-eligible.
- Store verified Ayah state, corrections and audit history as SHA-256-bound overlays; reject source mismatches and invalid/conflicting boundaries. A correction changes the effective timeline, not the immutable base file.
- On deployment, persist live reviews through a Docker host bind mount; provision its directory through the host Docker daemon with UID/GID 10001 and mode 0750 before replacing the backend. Image-bundled Git review JSON seeds only absent files. Never overwrite an existing server review file with the image copy.
- Publication of reviewed data to GitHub happens manually from the server terminal after inspection; no Git credentials or automatic push logic inside the app.
- Stream large MP3s progressively with verified end-time guards and HTTP ranges; retain service-worker chunk caching where supported. Playback must not require downloading a whole long Surah first.

## Security & Runtime
- Publish **one** website origin. Angular uses fixed same-origin `/api/*`; frontend Nginx proxies to FastAPI on the private Docker network. No separate public API hostname or host-published backend port for MVP.
- Admin writes require original browser origin; proxies preserve Host and HTTPS scheme. CSRF and rate limits remain. Localhost read-only GET CORS is permitted for Design Canvas development only; no configurable CORS origin secret.
- Administrator password comes from the Woodpecker runtime secret `ISLAMTROVE_ADMIN_CODE`, never from source, frontend, or a Docker image. Constant-time comparison, rate limits, HTTPS/same-origin and CSRF remain; Docker admins can inspect env.
- Keep secrets, local recordings, generated candidates, and developer caches out of public Git/Docker contexts; preserve approved canonical and review JSON.

## Build & Deployment
- Use the existing Nx + npm Angular workspace and uv-managed FastAPI backend. Tests and type/lint checks are local development operations, **not** steps in Woodpecker deployment.
- Mirror `mcp-registry`: separate frontend and backend Woodpecker pipelines, triggered by `main` changes, directly build Docker image → force-remove previous container → start new container → remove outdated service images. No extra rollout script or automatic rollback.
- Frontend is served from unprivileged Nginx, bound to host loopback (the server's HTTPS reverse proxy supplies public ingress). FastAPI stays accessible only to containers attached to the IslamTrove Docker network.
- Production review files survive container replacement; back up the persistent host directory independently. Do not deploy or publish without explicit user authorization.
